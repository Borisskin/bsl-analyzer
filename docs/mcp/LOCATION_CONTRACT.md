# Location contract v1: одно место и один конверт на все инструменты

До этого контракта каждый инструмент писал «где» по-своему: `search` — 1-based строки
без колонок, `diagnostics` — 0-based диапазон с колонками, но без пути и корня в самой
находке, `symbol_info` — одну строку 1-based при 0-based входе того же инструмента,
`graph` — вообще ничего. Потребитель обязан был знать, с кем разговаривает, прежде чем
прочесть ответ.

Теперь место и свежесть описываются одинаково везде, и сериализует их один модуль:
`crates/mcp-server/src/tools/location.rs`. Инструмент собирает типизированное значение
и отдаёт его туда; ключи он не пишет.

## Объект места

```jsonc
{
  "root_id": "",                        // обязателен; "" = основная конфигурация
  "path": "CommonModules/Продажи/Ext/Module.bsl", // относительный к root_id, разделитель "/"
  "range": {                            // опционально
    "start_line": 119, "start_character": 10,
    "end_line": 119,  "end_character": 22
  },
  "enclosing_range": { "…": "…" },      // опционально
  "position_encoding": "utf-16",        // обязателен, константа
  "module": { "kind": "ОбщийМодуль", "name": "Продажи" }, // опционально
  "schema_version": "1"                 // версия ПЛИТЫ, не инструмента
}
```

- **0-based, конец исключающий** — как в LSP и SCIP.
- **Колонки — кодовые единицы UTF-16**, и это объявлено полем, а не подразумевается.
  Единица важна: у одного и того же места есть три разные «колонки» — байтовая,
  в кодовых точках и в кодовых единицах, — и они расходятся на символах вне BMP.
- **Пара `(root_id, path)` — ключ файла.** Расширение повторяет структуру каталогов
  конфигурации, поэтому один относительный путь живёт в нескольких корнях. Пустая строка
  — зарезервированный идентификатор конфигурации.
- **Два диапазона.** `range` — имя символа; `enclosing_range` — весь узел. У находки
  диагностики имени нет, поэтому там `range` — спан самой находки, а `enclosing_range` —
  метод, который её держит.
- **Диапазоны опциональны.** Локация без них означает «файл»: так отвечают хит поиска из
  общего baseline, карточка модуля и всё, у чего позиции в источнике нет. Ноли вместо
  отсутствия были бы неправдой.

### Место в ответе про один файл

Когда ВЕСЬ ответ про один файл — как у `outline`, — пара `(root_id, path)` вместе с
`position_encoding` и версией плиты публикуется один раз, в корневом объекте места. Узлы
такого ответа несут только `range` и `enclosing_range` в тех же единицах; узел адресуется
парой из корня плюс своим диапазоном.

Это не другая плита, а та же: повторять пару у каждого узла значило бы платить сотней с
лишним байт за узел ровно тем же самым значением. Что при этом обязано остаться — объявление
единиц: без него узловые диапазоны стали бы подразумеваемыми, а подразумеваемая колонка
расходится с фактической на первом же символе вне BMP.

### Когда места нет

Вместо `location` приходит `location_unavailable` — машинный код, а не молчание:

| Код | Когда |
|---|---|
| `no_source_location` | у сущности нет файла по построению: объект метаданных, форма, реквизит |
| `roots_unavailable` | у ответившего снимка не было таблицы корней (загрузка опубликовала кэш графа раньше, чем загрузился проект) |
| `path_outside_registered_roots` | путь не принадлежит ни одному зарегистрированному корню |
| `absolute_path_without_pair` | у источника абсолютный путь там, где ожидалась пара: файл назван, но не как `(root_id, path)` |
| `relative_path_without_root` | известен только относительный путь, и поставить его в корень нечем. Зеркало предыдущего кода, и потому код отдельный: одно имя на два противоположных факта не даёт потребителю сказать, что именно случилось |
| `source_path_unavailable` | файл у сущности ЕСТЬ, но назвать его путь нельзя: запись VFS не выражается строкой либо отсутствует в наборе файлов корня. Отличается от `roots_unavailable`: таблица корней была на месте, не было пути |
| `no_call_site` | у ребра графа нет вызова в коде: связь выведена из метаданных, а не прочитана из тела. Спана нет и не будет |
| `call_site_not_recorded` | ребро стоит за написанным в коде, но спан этого места сборка не хранит. Отдельный код именно потому, что общий с предыдущим научил бы потребителя перестать ждать спан, который следующая сборка способна дать |
| `source_drifted` | файл уехал под записанным спаном. Опубликованный диапазон был бы правдоподобным и неверным — а по нему режут текст |

У сущности, у которой место есть по построению, ровно один из двух ключей присутствует
всегда.

Три последних кода появляются только у мест ВЫЗОВА на рёбрах `graph`: у них спрашивают
не адрес сущности, а точку в тексте, и её отсутствие имеет свои причины.

### Откуда берётся `root_id`

Две ветви, и это не деталь реализации, а обещание:

- **Корень выводится из пути** (`symbol_info`, `diagnostics`, `graph`): на входе только
  путь, пара строится по таблице корней. Файл вне всех корней локации не получает.
- **Корень приходит от источника** (`search`): он уже лежит в хите и копируется как есть,
  без проверки на регистрацию. Хит из общего baseline несёт корень чужого воркспейса —
  подменить его пустой строкой значило бы соврать, а отбросить локацию — потерять адрес,
  который источник знает, а мы нет. Такая локация в этом воркспейсе обратно не
  разрешается: `diagnostics file` по ней ответит `unknown_root`, и это честный отказ.

## Конверт

```jsonc
"freshness": {
  "source": "resident" | "graph" | "search-index" | "file-parse" | "name-dictionary",
  "revision": 42,                          // null, когда у источника нет своей идентичности
  "topology_fingerprint": "0a1b2c3d4e5f6071", // 16 hex-знаков; null, когда неизвестен
  "stale": false,
  "completeness": {
    "status": "complete" | "partial",
    "reasons": [ { "code": "output_budget", "detail": "…" } ]
  },
  "drift_watch": "starting" | "watching" | "polling" | "unobserved" // только graph и search_code
}
```

- **Кто ответил — закрытый словарь `source`:**
  - `resident` — резидентная база анализа: своя ревизия, своя топология, свой вердикт дрейфа;
  - `graph` — хранилище графа вызовов;
  - `search-index` — индекс поиска; своей ревизии у него нет;
  - `file-parse` — один файл, разобранный ради этого вызова, и ничего больше: ни индекса, ни
    резидента, ни графа. Своей идентичности у такого разбора нет — нет ревизии, которой он
    принадлежит, и нет топологии, при которой он снят, — поэтому `revision` и
    `topology_fingerprint` приходят `null`, а не заимствуются у соседа;
  - `name-dictionary` — сразу несколько артефактов, у каждого своя ревизия: поиск по имени
    спрашивает таблицы модулей, перечень метаданных, платформу и граф одним вызовом. Одной
    ревизии, которая описывала бы такой ответ, не существует, поэтому `revision`,
    `topology_fingerprint` и `stale` приходят `null`, а состояние каждого источника едет в
    поле `providers` самого ответа. Занять ревизию у одного участника значило бы объявить
    свежими четырёх остальных.
- **Отпечаток топологии — строка**, а не число: значение 64-битное, и JSON-число у
  JS-потребителя молча теряет точность выше 2⁵³.
- **`revision`/`topology_fingerprint`/`stale` бывают `null`.** У поиска нет собственной
  ревизии; проставить ему ревизию резидента или графа значило бы выдать чужую свежесть за
  свою — ровно то, против чего заводится контракт. Поле `source` называет, кто отвечал.
- **Полнота собирается там, где факт известен** — из возврата функции обрезки, флага
  предела, счётчика непрочитанных, — и никогда не восстанавливается разбором уже
  собранного JSON.
- **`drift_watch` — на чём стоит вердикт `stale`.** Ключ пишут только источники, которые
  сами следят за воркспейсом: `graph` и индекс поиска в `search_code`. Конверты остальных
  источников не изменились ни на байт. Закрытый словарь:
  - `starting` — наблюдатель источника ещё не закончил первый взгляд на воркспейс;
  - `watching` — каждое изменение, доставленное наблюдением, доходит до источника;
  - `polling` — наблюдение не поднялось целиком или части воркспейса: изменения находит
    периодический обход с контентной сверкой, и правка, не изменившая размер и время
    записи, видна не позже одного его цикла;
  - `unobserved` — наблюдатель остановился: изменения с тех пор не замечаются.

  Источник, за которым никто не следит, не может знать, что отстал, поэтому при
  `starting` и `unobserved` граф отвечает `stale: true` — раньше в этих состояниях он мог
  назвать себя свежим. Это исправление ложного «свежо», а не новый смысл поля: `stale`
  по-прежнему значит «ответ может не отражать диск»; поэтому изменение минорное. У индекса
  поиска своей ревизии нет и `stale` остаётся `null`, поэтому то же сообщает полнота:
  `search_code` при `starting` и `unobserved` отвечает `completeness: partial` с причиной
  `modality_degraded`.
  В `polling` граф добавляет к прежним причинам просроченный обход (старше двух периодов
  опроса).

### Словарь причин неполноты

Закрытый: новый код — это новая версия плиты, а не новая строка на месте.

| Код | Что означает |
|---|---|
| `output_budget` | ответ обрезан бюджетом вывода; поднимите `max_output_tokens` |
| `result_cap` | сработал счётный предел (`max_findings`, `max_nodes`, предел кандидатов) |
| `index_building` | нужный части ответа индекс ещё строится |
| `unreadable_files` | какие-то файлы прочитать не удалось |
| `out_of_analysis_scope` | часть запроса вне настроенной области анализа |
| `modality_degraded` | подсистема, которой ответ обычно пользуется, была недоступна |
| `owning_configuration_missing` | файл принадлежит внешней обработке или отчёту, а основной конфигурации у проекта нет: обращения к ней помечены как неразрешённые |

### Отмена вызова

**Отмена — не причина неполноты, а отсутствие ответа.** Кода для неё в словаре выше
нет, и он не появится: неполнота описывает тело, которое клиент получил и может
читать, а отменённый вызов тела не производит вовсе.

Клиент отменяет вызов уведомлением `notifications/cancelled`. После этого на провод не
уходит **ничего**: ни тела, ни конверта `freshness`, ни причин неполноты — и ошибки
тоже. Транспорт отбрасывает ответ на идентификатор, отмену которого уже обработал, как
того и требует спецификация от получателя. О снятии работы вызывающий знает по
собственному уведомлению, а не по ответу.

**Так отвечает всякое чтение резидентной базы**, а не избранные инструменты:
`references`, `symbol_info`, `metadata` (`info`/`tree`/`object`), `graph` с
`action=resolve` и `diagnostics` в обоих действиях, `file` и `workspace`. Это
свойство пути, а не список: резидент читается ровно одной дверью, и мимо неё чтение
не компилируется, поэтому следующий инструмент получит то же поведение по
построению, а не по договорённости.

Причина именно такая, а не «отдать что успели»: по спецификации MCP клиент, пославший
`notifications/cancelled`, обязан игнорировать пришедший следом ответ. Частичное тело
после отмены — это работа, которую никто не прочитает, и обещание полноты, которого
никто не проверит.

**Поиск отвечает так же, и тоже одной дверью.** `search_code`, `find_docs` и
`search_docs` в обоих профилях идут через `search_call`: тело работает на блокирующем
потоке под тем же per-request токеном, исход рендерится тем же `cancellable_answer`.
Разница с резидентом только в том, как сигнал доходит до тела: у поиска нет запросов
salsa, которые раскрутились бы, а замок движка — обычный `Mutex`, который раскрутка
отравила бы, — поэтому тело наблюдает клон токена само и возвращает отмену значением
из ближайшей кооперативной точки. Точки стоят там, где вызов действительно ждёт: в
ожидании замка движка, в ожидании ответа baseline-актора, в ожидании эмбеддинга
запроса, между раундами дозапроса к базе и между dirty-путями prefetch. Отменённый
запрос отпускает всё, что держал, — и никого не трогает: запрос актора, ещё не
начатый, пропускается, а начатый доделывается и отвечает в никуда.

Предел этой отмены — именованные ожидания, а не всё подряд. Ожидание замка, актора и
эмбеддинга выходит по отмене не позже одного опроса (25 мс); отмена, пришедшая ВНУТРИ
синхронного вызова без точки — чтение резидента, один локальный запрос к движку под
замком, один PG-запрос в работе на воркере, — наблюдается на его выходе. Сам HTTP
эмбеддинга не прерывается: он уходит на поток-помощник, который ничего не держит и
доживает свой таймаут вхолостую.

**Отмена клиентом и снятие сервером — разные исходы.** Если вызов сняла не отмена, а
собственная перестройка сервера, придёт retry-конверт: клиент, который ничего не
отменял, обязан получить ответ, а не молчание.

Получить содержимое, посчитанное до отмены, — сценарий расширения
`io.modelcontextprotocol/tasks` (`docs/mcp/TASKS.md`): там у работы есть отдельный
дескриптор, и терминальный статус может нести результат. Это вторая ветка исполнения,
доступная только объявившему расширение клиенту, и в синхронной ветке, описанной
здесь, она ничего не меняет.

## Старые поля

Ничего не удалено и не переименовано. Новые ключи добавлены рядом, старые помечены
устаревшими и будут жить до следующей мажорной версии схемы своего инструмента.

| Инструмент | Устаревшее | Взамен |
|---|---|---|
| `search` | `line_start` / `line_end` (1-based, конец включающий) | `location.enclosing_range` |
| `diagnostics` | `range` (0-based, колонки в кодовых ТОЧКАХ) | `location.range` |
| `diagnostics`, `graph` | `revision`, `stale` в корне конверта | `freshness.revision`, `freshness.stale` |
| `symbol_info` | `definition` (одна 1-based строка, без корня) | `definitions[].location` |

Значения устаревших полей не изменились ни на единицу: тесты утверждают старое и новое
рядом, на одном ответе.

## Версии

Три независимые оси, и путать их не нужно:

- `contract_version` (`bsl-analyzer contract`) — что сборка ПРИНИМАЕТ: инструменты,
  действия, параметры;
- `schema_version` ответа инструмента (`search_code` `"5"`, документационные действия
  `reference`-профиля `"4"`, `diagnostics` `"16"`, `graph` `"34"`) — форма ответа этого
  инструмента;
- `schema_version` внутри объекта места — версия самой плиты, общая для всех инструментов.

Плита versionируется отдельно именно потому, что путешествует между инструментами: её
нельзя версионировать номером одного из них.

**Добавление кода в словарь причин плиту НЕ двигает.** Это ровно случай «добавлено
принимаемое значение» из правила бампа контракта, то есть minor у `contract_version`.
Потребителю, разбирающему словарь исчерпывающе, новый код виден по минорной версии; форма
плиты при этом не меняется, и двигать её номер значило бы объявлять изменение всем
инструментам сразу ради того, что не касается ни одного из них.

## Что этот этап не закрывает

- Профиль `reference` (`search action=find_docs|search_docs`) остаётся как был: его хиты
  указывают в HTML-файлы справки платформы, у которых нет ни корня, ни BSL-узлов.
- У header-чанка поиска диапазонов нет: его конец строки считается другим правилом, чем у
  чанка метода, и выдавать его как исключающий конец было бы числом, которого контракт не
  имеет в виду.
- `search` не выставляет `result_cap`: усечение по `limit` происходит внутри слияния
  модальностей, и до сериализации доезжает уже урезанный список. Вывести причину из
  равенства «показано = запрошено» значило бы гадать.
